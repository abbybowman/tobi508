How TOBI tests a page

TOBI follows the DHS Trusted Tester 5.1.3 procedure in a real Chrome browser. Rules decide outcomes; a model only answers the narrow questions a rule asks; anything it is unsure of goes to a person.

  • Browser TOBI drives Chrome
  • Rule a written rule decides
  • Model TOBI's pinned model answers a question
  • Person a person settles it

One path for every test

All 22 tests TOBI performs follow the same path. What differs between tests is how the evidence is collected and how much a rule needs a judgment.

  1. Record the page onceBrowser

    In real Chrome. Every check after this runs on the recording, so key presses and form entries never reach the live site, and the same recording gives the same evidence.

  2. Walk the page and take an inventoryBrowser

    One keyboard walk, Tab forward and Shift+Tab back, shared by every test. Focus is read from Chrome itself, so a page script cannot fake it. The inventory lists what the page holds, inside frames and web components too.

  3. Collect the test's own evidenceBrowser

    Pictures, key presses, form entries, a period of watching, or other pages of the site: one of five families, below.

  4. Rules decide what they canRule

    Each test has one rules file. Its rows are tried in order and the first that matches decides; each row cites the step of the Trusted Tester PDF it rests on.

  5. A rule asks an open questionModel

    Only when the procedure calls for a judgment. The model gets the evidence, the pictures and a rubric with examples, and answers yes, no or unsure. Page text reaches it only marked as untrusted.

  6. The rule uses the answerRulePerson

    A sure answer goes back to the rule, which decides. "Unsure", or a call that failed, goes to a person.

  7. Hold back anything not fully readRule

    If a test did not read everything the inventory holds, a PASS or DOES NOT APPLY becomes NEEDS REVIEW, with a sentence saying what was not checked. Never the other way round.

  8. Report by Trusted Tester testRule

    Findings in plain language with their evidence, and a draft in the same rows as DHS's SCRT, marked "not certified by a Trusted Tester".

4.D Focus visible: the model looks at pictures

The Trusted Tester PDF (p. 22) asks the tester to move focus to each element and check that they can see where focus is. TOBI does the same, and measures the change before it asks anyone.

  1. Tab to each elementBrowser

    The shared keyboard walk reaches every element that takes focus, forward and back.

  2. Take three pictures of itBrowser

    Without focus (A), with focus (B), and the pixels that differ (C). On a page that moves by itself, TOBI looks twice and ignores pixels that change on their own, so a slideshow behind a link cannot count as its focus indicator.

  3. Rules decide the clear casesRule

    The first row that matches decides:

  4. The model looks at the picturesModel
    "Image A shows part of a web page without keyboard focus; image B shows the same part with keyboard focus on the outlined element. Image C marks the pixels that differ. Is there a change on or right around the outlined element in B that a sighted user would notice as showing it has focus?"
    From the rubric the model is given

  5. The rule uses the answerRulePerson

    Yes: PASS, because TOBI also measured a change. No: FAIL. Unsure: NEEDS REVIEW, for a person to look.

  6. The page's resultRule

    Any element that fails makes the page FAIL, listing each one. Otherwise, any element left for review, or a walk that did not reach every element, makes it NEEDS REVIEW. Only when every element passes is the page a PASS.

4.C No keyboard trap: the model reads, then TOBI presses the key

The Trusted Tester PDF (p. 21) asks the tester to move through the page with the keyboard and, where focus gets stuck, try the standard keys and then any key the page documents. A scanner cannot do this: it never presses a key.

  1. Walk the whole page, both waysBrowser

    Tab forward through the page from a fresh load, then Shift+Tab backward from another. A trap is focus stuck on one element, or circling a few, never reaching the rest.

  2. Make sure the trap is realRule

    A second walk from a fresh load must find it again. A trap seen only once is NEEDS REVIEW.

  3. Try the standard ways outBrowser

    Each from a fresh replay of the steps that reached the trap: the opposite direction, the arrow keys, Esc then Tab, and Enter on each control in the trap. If focus leaves, PASS. Leaving the page itself (a reload or a new page) is not a way out.

  4. The model reads the page for a documented keyModel
    "Does this text tell users a specific key or key combination that moves keyboard focus out of this section? If yes, give the keys, the exact quote and where it appears."

    A shortcut list with no exit key counts as no. Text a user cannot perceive does not count.

  5. TOBI presses that keyBrowser

    On a fresh replay. If focus leaves, PASS. If not, the model's answer counts for nothing.

  6. A loop of form fieldsModelPerson
    "Does this section ask the user to enter or choose something before they can continue?"

    A consent box or a required field can hold focus on purpose. If the model says yes, the result is NEEDS REVIEW, with the values a person should try.

  7. Nothing workedRule

    Stuck, or looping, with every way out tried: FAIL. The page fails if any trap fails; it passes only when both walks finished and every trap had a way out.

Two tests, two jobs for the model

4.D Focus visible

The model looks at three pictures.

What backs it: TOBI measured a change before asking.

4.C No keyboard trap

The model reads the page's text.

What backs it: TOBI presses the key it found.

In both, the model never decides an outcome. It answers one narrow question; the rule decides; "unsure" goes to a person.
