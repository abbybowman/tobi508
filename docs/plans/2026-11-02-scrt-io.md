# Plan: SCRT report files (read, write, compare, review, export) (2026-11-02, Phase 1 built)

Gives the server a report file format a Trusted Tester (TT) already knows,
so results can be saved, merged, compared, reviewed by a person and, once
a certified TT has validated every row, exported as a real SCRT file.
Replaces the ROADMAP's `read_report` item for SCRT (ACRs and OpenACR are out
of scope: they are product-level, and this tool works per page).

## Decisions (Abby, 2026-11-02)

1. **Files are SCRT JSON**, plus an HTML view for the calling agent to show
   its person. One file per page; the server rolls pages up to the site.
2. **A fork, "pre-SCRT"**, that keeps SCRT's shape and field names where
   they mean the same thing, cleaned up for Python, and that SCRT cannot
   load. It carries a prominent disclaimer, where each row came from, the
   rows that need a person, and their screenshots.
3. **NEEDS_REVIEW rows** have a blank result, a note and a screenshot when
   there is one.
4. **Review is by a person in a local HTML page** that works like SCRT's
   (load a template or file, edit, save as a local file), with a
   "reviewed and validated" checkbox at the end of each row.
5. **A person's answer always wins** over the tool's; every row records its
   source.
6. **Export to real SCRT only when every row is checked** and the TT's
   details, including their TT certification number, are filled in. The
   export's `P_Notes` says the report was prepared with agent assistance
   and reviewed by the TT (like naming ANDI as a tool).
7. **Comparison:** Abby's blind SCRT files are the answer key, scored with
   the categories `tests/scoring.py` uses (agreement, false PASS, false
   FAIL, NEEDS_REVIEW rate). Changed 2026-11-03 (Abby, after code review):
   the comparison itself is neutral (`compare.py`: what each file says,
   what changed; usable before and after a fix), and the answer-key
   scoring sits on top of it in `evals/scoring.py`.
8. **Reading both formats:** SCRT and pre-SCRT. A user may bring a TT's SCRT
   report they need help understanding and fixing.
9. **Two audiences, one file.** TTs get the review page; project managers
   and developers get a static, plain-language report ordered by impact
   (SCRT's `DisabilityImpact`, and site-wide before single-page). Fix advice
   is a separate, optional tool.
10. **Order:** judging first (Abby has finished blind evaluations), then
    TT review and export, then site roll-up and the developer view.

## The pre-SCRT file (`pre-scrt/1`)

A top-level **object**, not SCRT's one-item array, so SCRT's
`jsonData[0]` finds nothing (checked against the vendored SCRT in a test,
not assumed). Pydantic models in `src/tobi508/scrt.py`:

```
PreScrt
  format: "pre-scrt/1"
  disclaimer: NOT_CERTIFIED_DISCLAIMER       # same text as Report
  certified: Literal[False]
  Product:  P_Name, P_Version, P_Owner, P_Type, P_Location (the page URL),
            P_Desc, P_Notes                  # SCRT names, typed, None not " "
  System:   os, browsers: list[{name, version}]   # SCRT's flags, split
  Tester:   T_fstnm, T_lstnm, T_companyname, T_cntc, T_ID (TT cert number),
            T_Role, T_scope, T_Date          # empty until a person fills it
  T_eval: "Agent-assisted (not a Trusted Tester evaluation)"
  T_evalMthd_Vrsn: "v.5.1.3"
  site: {name, pages: [urls]} | None         # set when part of a site family
  runs: [{run_id, report_sha256, versions}]  # every run merged into the file
  Criteria: [Row]                            # 61 tests, child rows allowed

Row
  TestID (normalized, checked against catalog), TestName, Test, CrtID,
  Guideline, TestCondition, DisabilityImpact: list[str]   # from template
  TestResult: Pass | Fail | Does Not Apply | Not Tested | None (blank)
  needs_review: bool                         # tool's NEEDS_REVIEW, shown highlighted
  TesterComment, location, GlobalIssue: None | Yes | No
  ImageSrc, ImageSrc2: data URL | None
  RemediationDetails, RemediationDate
  parent: int | None                         # child issue of row n
  source: {by: tool | person, run_id, spec_version, rows, decided_by}
  review: {checked: bool, by, at} | None
```

Mapping from `Report`: PASS → Pass, FAIL → Fail, DNA → Does Not Apply,
NOT_TESTED → Not Tested, NEEDS_REVIEW → blank with `needs_review` and the
finding's plain summary as `TesterComment`. One Fail row per failing
instance (child rows), each with its screenshot. Tests the run did not
select or cannot perform are blank and `needs_review`, with "This test could
not be performed" and the reason. No outcome is decided here: the mapping
copies the spec's outcome (principle 2).

Screenshots are inline data URLs so the one file is self-contained (and
SCRT needs them that way on export). A size cap per file (setting) keeps
the first screenshots per row and notes how many were left out; the
`run://` report still has them all.

## Order of work

### Phase 1: judging (built)

Steps 1-6 are built: the vendored SCRT (`third_party/scrt/`), the reader
and writer (`scrt.py`), `compare.py`, the `tobi_read_report` tool and the
judging procedure (`evals/judging.py`;
[how to run a round](../how-to/run-a-judging-round.md)). What the SCRT
files taught us is in [solutions/scrt-format.md](../solutions/scrt-format.md).

### Phase 2: TT review and export

7. **`review.html`**: a static page like SCRT's create page. It loads a
   pre-SCRT file (or a template), shows rows needing a person highlighted
   with their screenshots, lets the TT edit results, comments and locations,
   add child rows and screenshots, tick "reviewed and validated", fill in
   tester details, and saves the file as a download. Changing a row's
   result or comment clears its tick and sets `source.by = person`. Text
   from tested pages is shown as text only (never `innerHTML`): a hostile
   page must not run script in the TT's review page. No network requests.
   Served by the MCP as a resource and saved by the client.
8. **Merge**: `tobi_run_tt_tests` takes an optional partial file (pre-SCRT
   or SCRT) for the same page. New tool rows fill blank rows and replace
   older tool rows; person rows always win and conflicts are listed.
9. **Export**: converts a pre-SCRT file to SCRT 5.2.0 JSON only when every
   row is ticked, no row is blank, and the tester fields including the TT
   number are filled in (the TT's attestation; the gate is a policy, not
   tamper-proofing, and the plan's docs say so). Writes `OptMenu1` from the
   template, the TT's details, and the `P_Notes` line. A test loads the
   export in the vendored SCRT and opens its view page.

### Phase 3: site roll-up and the developer view

10. **Site roll-up** from several pages' files: per test, which pages fail;
    `GlobalIssue = Yes` where the same issue fails on every page given (and
    9.A-9.C, which are site-level), keeping a person's Yes/No as set. Later:
    site-wide code issues vs page-specific code vs page-specific content.
11. **Developer and project manager report**: static HTML (a Docs export
    can follow), plain language, no spec codes, ordered by reach (site-wide
    first) and SCRT's `DisabilityImpact`; rows needing a person shown as
    "a person should check this", never as passes or likely failures. Links
    to the separate fix-advice tool when that exists.
