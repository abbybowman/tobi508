## A defect found while reading (fix in PR 3; verified by running it)

`Check19A.follow_up` builds `other_pages = (given + suggested)[:5]`. When
the caller gave 5 or more pages, the suggested ones are cut off: with the
8 pages the runners give on round 1, the call carries 5 of the given pages
and **no suggested page** (ran `Check19A().follow_up` on a state with 8
given pages and 2 suggestions). So making the follow-up call as the code
stands would change nothing. Fix: suggested pages first, then the given
ones, up to the cap of the mode the call runs in (`OTHER_PAGES_NO_LIMIT_MAX`
= 50 with `no_time_limit`, which the server's follow-ups use by default;
5 otherwise, still suggested pages first). Code only: the spec already
says the call adds the suggested pages.

## PR 1: a suspected alias of T (19.A 1.10.0)

### Terms (new entries, after *T*)

- *Suspected alias* (1.10.0; Abby, 2026-11-14: a tester treats
  `/cilab/index.html` as `/cilab/`; round 2 p05): the destination of a
  link on another page the test read (a caller's page, a suggested page
  passed back, a search results page) that is not T but differs from T
  only in one or more of these ways: its last path segment is a file
  named `index.*` or `default.*` where T's path ends in `/`, or the
  reverse; its scheme (`http`, `https`); a leading `www.` on the host; its
  query string. Any other difference (another directory, another file
  name, another host) is not an alias. A link on T itself is not counted:
  a link from T to T is no way to reach it.
- *Alias check* (1.10.0): only when the links to T (W1) and W5 give fewer
  than two kinds and a suspected alias exists. At most 3 a run, taken in
  the order their links are read (other pages in order, each in reading
  order). Each is loaded exactly as a caller's other page is loaded, by
  the same code: the allowlist on every redirect hop, T's host before and
  after redirects, its own HAR, the page cache, the 20 s share a
  caller-named page gets. It is *the same page as T* when its final
  address equals T's (fragment and trailing slash aside), or its recorded
  document is byte-for-byte T's, or the near-copy comparison holds for the
  pair (`site.near_copy`, generalised: the share of text keys the two
  pages have in common is at least `NEAR_COPY` = 0.9; see "Decision
  needed" below). It is *a different page* when it was loaded and read
  and none of these holds. It is *not verified* when it could not be
  loaded (not allowed, another host after redirects, no recording in
  replay mode, an error, out of time) or read, or was beyond the 3 checked.
  A *verified alias* is one that is the same page as T. The alias's own
  links are never read or followed.
- *Leads to T* (amended): a link leads to T when its destination equals T
  or a verified alias of T (absolute, fragment dropped, trailing slash
  ignored).

### Decision needed (near-copy for an alias pair)

`near_copy` today compares all text keys of two pages, and only for the
same path with another query string, where it was measured (same page
1.00, highest different page 0.44, on NASA search pages). An alias pair
can be two different pages under one template: on a thin page the shared
header, menus and footer can be most of the keys. With 200 template keys
and 10 content keys on each page, the share is 200 / 220 = 0.91, a false
match and, through W6, a possible false PASS (principle 3). I propose the
alias pair is compared on **content only**: the text keys of units outside
navigation, banner and contentinfo regions, and *not verified* when either
page has fewer than 5 such keys. The A2 use of `near_copy` stays as it is.
The fixture "an `index.html` that is a different page" is built on exactly
this case (a thin page under a heavy template).

## PR 2: suggested pages widened (19.A 1.11.0)

### Terms, *Suggested pages* (replaces the entry)

- *Suggested pages*: pages of T's host that could show more ways and were
  not given, in this order, at most 5 in all (1.11.0; Abby, 2026-11-14: a
  tester goes down to a child page for a breadcrumb or a link back, up to
  the parent, and to the home page):
  1. *site map*: links on the pages read named "site map", "sitemap" or
     "A-Z index";
  2. *T's parent*: the address one level up from T's own path, on T's
     host (`/a/b/c/` and `/a/b/c.html` give `/a/b/`; `/a/b/index.html`
     gives `/a/`; T at the root has none). It comes from T's address, not
     from page content;
  3. *the home page*: a link to the site's root, or named "home";
  4. *child pages*: up to 2 links on T, on T's host, whose path is under
     T's own directory (T's path when it ends in `/`, else its path up to
     the last `/`) and is not T, that directory, or a suspected alias of T;
     links to files that are not pages (an extension other than none,
     `html`, `htm`, `shtml`, `php`, `asp`, `aspx`, `jsp`, `cfm`) are left
     out; the first two in T's reading order;
  5. *breadcrumb links* on the pages read.

  The same address twice, a page already given, T and a suspected alias of
  T are left out. They are proposed to the calling agent ... (as 1.1.1).
  The follow-up call reads them as other pages, for links to T or to a
  verified alias of T; the server makes it itself when the agent calls
  `tobi_run_status` with `finish=true` (unchanged), and the eval runners
  make it once per page (PR 3).

Why this order: a site map is a second kind on its own (W1 *site map*),
so it is the likeliest to decide; the parent most often links T in its
content (*links between pages*), a kind the template's navigation never
gives; the home page and the children mostly add *navigation* (menus,
breadcrumbs), which the given pages usually show already. When the cap
bites, the breadcrumbs go first; they are mostly ancestors the parent and
home page already cover.

## PR 3: the eval runners make the follow-up call

- `evals/apijudge_gate.run` and `evals/judging.scan`/`apply` (when a page
  is finished): for each page, once, take the calls the server may make
  itself (`pipeline.server_may_make`) from its report and make them with
  the same function `tobi_run_status` uses (`_start_follow_ups`'s call,
  factored so both use it), with the server's default `no_time_limit`.
  The follow-up's 19.A finding replaces the first one in the kept
  `report.json` and `pre-scrt.json`, as the agent is told to do ("Replace
  this result in the saved report"); the first finding, the call and the
  follow-up's run id are recorded beside it (`follow_up.json`), and in
  `report.follow_ups_made`. A follow-up that fails is recorded with its
  error; the first finding stays.
- `tested_frozen` mode (the gate, the agent eval): the follow-up's pages
  and alias checks load live under the usual rules. `replay` mode: a page
  with no recording is a refused follow-up (the first finding stays,
  NEEDS REVIEW), and an alias with no recording is *not verified* (W7).
- Gate 2026-11-14, cells on G3: 8, all round 1 (p01 to p05, p07 to p09;
  keys: 6 Pass, p02 Does Not Apply, p03 Fail). Round 2 has none on G3:
  its four NEEDS REVIEW cells (p06 to p09) are G5 (the search found the
  page, nothing else). **With the code as it is, the follow-up would have
  changed 0 of the 8**: each run had 8 other pages, so the call carried
  no suggested page (the defect above). With the fix, each call adds
  `https://www.nasa.gov/` and `https://www.nasa.gov/sitemap/` (the
  suggestions the round 1 runs named), loaded live; how many of the 8 then
  move I can say only by running it.
