# Rules spec: Test 4.A (2.1.1-keyboard-access)

The tool gives each page one 4.A outcome: PASS, FAIL, DOES NOT APPLY or NEEDS REVIEW. It never emits NOT TESTED: the PDF allows NOT TESTED only where a test names it (p. 6), and 4.A does not.

**Citations.** Printed page numbers of TT 5.1.3 (text also in `tt://5.1.3/tests/4.A`). HtT = How to Test step; ER = Evaluate Results item. 4.A is on pp. 19–20: identify functionality and essential information with the mouse, touch, voice or documentation (HtT 1.a), and title attributes on focusable elements (HtT 1.b); then access each with the keyboard (tab to it) and execute it (press Enter) (HtT 2); a title tooltip that does not appear within two seconds of focus is not revealed by focus (HtT 2.a); for an element without keyboard access, look for another keyboard method on the page with the same function (HtT 2.b); for essential information not reachable by keyboard, look for it elsewhere on the page (HtT 2.c). PASS if all functionality can be accessed and executed by keyboard (ER 1) and all essential information is keyboard accessible or available elsewhere (ER 2). Notes: changes that happen automatically or after interaction are included (ER Note 1); information is essential when it is needed to execute an action or understand information and relationships (ER Note 2); non-essential title information needs no keyboard access (ER Note 3).

**W3C sources.** [Understanding 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html): not every visible control must itself be focusable when the function is available by keyboard another way (its search form example: Enter in the field submits); a custom control that reacts only to Enter still satisfies the criterion. Failures [F54](https://www.w3.org/WAI/WCAG22/Techniques/failures/F54) (only pointing-device event handlers for a function), [F42](https://www.w3.org/WAI/WCAG22/Techniques/failures/F42) (emulated links not operable by keyboard), F55 (focus removed on focus; 4.E's evidence). ACT rules [akn7bn](https://www.w3.org/WAI/standards-guidelines/act/rules/akn7bn/) (iframe with interactive content excluded from the tab order) and [0ssw9k](https://www.w3.org/WAI/standards-guidelines/act/rules/0ssw9k/) (scrollable content reachable by keyboard). DHS publishes no TT results for either rule. These informed the decisions and fixtures only; the PDF stays the authority.

**Terms.** *Stop*, *OUT*, *BODY*, passes P1 and P2, stop identity and the settle rule are defined in [4c-no-keyboard-trap.md](4c-no-keyboard-trap.md). A *native control* is `a[href]`, `area[href]`, `button`, `input` (not hidden), `select`, `textarea`, `summary`, `[contenteditable]`, `audio[controls]`, `video[controls]`; the parts Chrome focuses inside a native date or time input (its month, day and year fields and its picker button, in the input's own shadow root; walk control `date` with the input as its group, 5.D spec V3) are part of that native input (1.2.0: they had been executed as custom controls, 28.8 s on the budget benefits form): they are not custom controls, focus on one reaches the input, and their `title` ("Show date picker") is the browser's, not a T instance (fixture F13). A *pointer target* is a visible element a mouse can hit (the element or a descendant is what `elementFromPoint` returns at its centre, followed through frames, so hidden, inert, covered and clipped elements are not targets) that is a native control; or has an interactive ARIA role; or has its own click, mousedown, mouseup, dblclick or pointerdown listener or `on…` attribute; or whose computed cursor is `pointer` when its parent's is not. A `<label>` for a control, `html` and `body` are never targets. A *custom control* is a stop that is a pointer target but not a native control. The *effect* of an action is any of: the top or a frame URL changes, a new page opens, a dialog becomes visible, focus moves, `aria-expanded` or `aria-checked` or `aria-pressed` or `aria-selected` changes, or the DOM changes, measured after the settle rule. Focus moving onto the element acted on (a click focusing it) is not an effect. A *media start* is an `<audio>` or `<video>` element, in any frame the tool can read, that was not playing (`paused` true or ended) before the action and is playing after the settle; it is an effect of a click, Enter or Space in this test only (1.4.0: a click that only starts a video changes nothing else on the page, so CILab's demo reel row was never a mouse-only control; a page whose video starts only on a click is F54). Tests 4.B and 5.D read no media: their *effect* is without it. A *pop-up* is a script dialog (`alert`, `confirm`, `prompt`) that opens, or a download that starts; it is an effect of a click, Enter or Space in this test only (1.9.0, review C-01: the browser closes a script dialog at once when nothing listens, and a download changes nothing on the page, so a control whose only effect was one read as "no effect" and was never a mouse-only candidate; the tool now listens for both during the action). Tests 4.B and 5.D read neither. The page's own changes are measured over `NOISE_MS` before the action; an effect that is only DOM changes on a page that changes on its own is unreliable (M1).

**Terms for row WK.** An element is *reached* when a pass this test has evidence from stopped on it: P1 and P2 (P6's stops are not passed to this test; 4.C spec section 6). The *elements to reach* are the elements Tab lands on when the last of those passes ended (`PassResult.inventory_end`: focusable, rendered, not disabled, not inert, not `tabindex="-1"`; a radio group, a date input and a frame the walk went into count once each). A pass that ended in a trap, a loop, a cap or out of time matters here only through what is left unreached: a page that grew is complete if everything present when the last pass ended was reached. The sentence is built by `walk.walk_coverage`, for example: "The keyboard reached 5 of the 6 elements on this page that take focus, so "Two" (a) was not checked. Tab got stuck at "Search" (textbox)." It names only what ran. An element Tab never lands on is one this test cannot have operated by keyboard, so it is left for a person; a radio Tab cannot land on (the rest of a group) is not such an element.

**Terms for the execute check** (1.16.0, issue #136 step 28). A *key-listening container* of a native control is the control itself or an element between it and `body` that has its own `keydown`, `keypress` or `keyup` listener (read as the walk extra reads click listeners: CDP, own node, the page's own world). `body`, `html`, `document` and `window` never count: a listener there is the page's keyboard shortcuts, not something wrapped round one control. The *changed region* of an action on a control is the lowest element that holds every element the action changed (children added or removed, an attribute or text changed; the walk's change log), leaving out changes to the element acted on and inside it; when nothing else changed, it is the element acted on. An effect *goes somewhere* when it holds a navigation to another address (a change of #fragment only is not one), a new page or a download. A key's effect *is the click's* when (a) for each of navigation, new page, download, script dialog, dialog and media start that the click's effect holds, the key's effect holds it too, a navigation to the same address (#fragment left out); and (b) when the click's effect does not go somewhere and changed the page (DOM), the key's effect changed it too and the two changed regions are the same element. Focus moving and a #fragment change are not compared, and a key that does more than the click (Enter also moves focus into the menu it opened) still does the click's. *Hedged reasons*: J1's reasons contain, ignoring case, any of "not certain", "uncertain", "not sure", "unsure", "unclear", "not clear", "not clearly", "not settled", "can't tell", "cannot tell", "can't confirm", "cannot confirm", "might", "maybe", "may be", "perhaps", "possibly", "probably", "likely" or "not the same" (round 3, MySearchStory: "alternative" with "The reached NASA link goes to nasa.gov, not the SDE home, so it is not the same ... Not certain.", and in a later run "not clearly the same ... Not settled.", each a PASS by M5).

**A key press that only scrolls** (1.21.0; #135 step 15; Abby approved 2026-11-23, option ii). In the execute check, a key press whose only change to the page is that the window scrolled and a layer positioned over the page (fixed, absolute or sticky) had its `style` set, or its `class` set to the value it already had, as a list or panel does to follow the scroll, has *no effect*. Space scrolls the page by default; round 3's SDE "All" list (ngx-bootstrap) sets its container's class again, unchanged, on each scroll step, so Space on an option read as "changes the page" and went to a person (M8r), while neither key chooses the option and a click does (key Fail, issue 10). Any other change, text, an element added or removed, a `class` that changed, another attribute, or a change on an element that is not positioned, keeps the effect. The risk taken: a real effect that only restyles a positioned layer during a scroll reads as none, which can move a cell toward FAIL (M10), never toward PASS. The sentence says which key only scrolled ("pressing Enter or Space does nothing (Space only scrolls the page)"). Fixtures F48 (M10 FAIL) and F49 (Space also marks the option outside the list: M8r, the effect is kept).

## 2. Evidence to collect

**From the shared keyboard walk** (`walk.py`): every stop with its frame chain, CSS path, tag, role, name, widget and title; P1's and P2's ends. Tabbing to each element (HtT 2, "access") is the walk itself.

**Walk extra** (cheap, no images): per stop, its `title` attribute, whether it is a native control, its own click-type listeners (CDP `DOMDebugger.getEventListeners`, own node only, read from the page's own world: from TOBI's isolated world CDP lists none of the listeners the page's scripts add, 1.4.0; listeners on ancestors such as `document` are delegation and are not counted) and its cursor.

**Pointer scan** (HtT 1.a; one fresh load after the walk). Every pointer target in the top document, every frame the tool can read and every open shadow root. Click-type listeners are read inside open shadow roots too (CDP `pierce`; 1.12.0, plan 2026-11-12 part D, review D-03: a mouse-only control inside a web component was never a target), and an effect is a change anywhere in the page, inside a server-rendered web component too (D-04: the walk's change log watches open shadow roots that no script attached). A target is *reached* when it is a stop of P1 or P2, is inside a stop, contains a stop, or is an item of a composite widget (menu, menubar, tablist, listbox, grid, tree, treegrid, radiogroup, toolbar) that an arrow probe reaches from that widget's stop. The *arrow probe*: fresh replay to the widget's stop, then ArrowDown (or ArrowRight if focus did not move) up to 20 times, as 4.D pass W, then the opposite arrow; at most `ARROW_MAX` widgets. A *native radio group* (1.19.0, issue #136; Abby, 2026-11-22) is a widget too: radio buttons (`input type=radio`) with the same `name` in the same form, or in no form, in one document, outside any composite widget. Tab enters the group once, at its checked radio button or at its first (Shift+Tab: its last), and the arrow keys move through it, so a radio button of the group that the walk did not reach is reached when the arrow probe from the group's stop lands focus on it; its stop is the radio button of the group that P1 reached. A press confirms it, so no question is asked; one the probe does not reach (a script stops the arrows) is a candidate as before. Round 1's search page: "Last Month" in the date filters was asked as J1 and judged to have no alternative, a FAIL against a Pass key. Fixtures F40 (arrows move: PASS) and F41 (a script stops them: J1). **A group whose change makes the page leave** (1.20.0, issue #136; Abby, 2026-11-22, option 1). Round 2's search page submits its form when a date radio button changes, so ArrowDown selects "Past week" and the page reloads: focus never rests on it, and the tool cannot load the page the reload goes to. Abby's key passes 4.A there (the arrows choose each filter) and fails 5.D for the reload. When the arrow probe leaves radio buttons of a group in the top document unreached, the *radio probe* runs: from the group's stop, on a fresh replay, one ArrowDown, and on another, one ArrowUp; each records every radio button that takes focus or changes as the press lands (a CDP binding, so it is read even when the page then leaves), waiting `RADIO_WAIT_S` (1 s). When both presses land on radio buttons of the group other than its stop, the arrow keys move through the group, the browser's own behaviour for a native radio group, so every radio button of the group is reached, those no press landed on too; otherwise only those a press landed on. The risk taken: a page that lets an arrow reach the next and the last radio button but blocks the ones between is passed. Fixture F43 (a group that submits on change: PASS). When 4.D's pass W, in the same call, reached every candidate of the widget with the same arrows from the same stop, those candidates are reached and no probe is made (1.2.0). Unreached targets are candidates.

**Hover scan** (HtT 1.a, mouse; ER Note 1; same load as the pointer scan). Move the mouse onto each stop, at most `HOVER_MAX`, settle, and record pointer targets that became visible; move the mouse away. A revealed target is reached when the walk reached it (a menu that also opens on keyboard focus) or when pressing Enter on the hovered stop reveals it too (one fresh replay per hovered stop that revealed something, at most `REVEAL_REPLAYS`). Otherwise it is a candidate, recorded with the stop that reveals it.

**Click check** (for each candidate that is not a native control, at most `CLICK_MAX`). Fresh load; hover its revealing stop if it has one; move the mouse onto the candidate; settle; click; record the effect. A native control is functional by definition (a link goes to its address) and needs no click.

**Scroll check** (1.8.0, post-round 2 fix 24; round 2: a carousel's scroll arrows made 21 of C's 62 unsure answers; Abby's carousel reading, fix 9). For each K candidate in the top document that is a pointer-only link or control a mouse can operate, that has no same-destination stop (M3) and that sits near a *scroller* (the pointer scan marks it: within four ancestors there is an element that scrolls, `overflow` auto, scroll or hidden with more content than room, that does not hold the candidate), at most `SCROLL_MAX` (8): fresh load; hover its revealing stop if it has one; record each scroller's position and its *items* (its children, through any single wrapper) with their boxes; move the mouse onto the candidate and click; wait `SCROLL_WAIT_MS` (700 ms: a smooth scroll) and settle; for each scroller that moved, the items that came into view (not in view before, in view now). The *revealed* items of the scroller that revealed most are *reached* when each is, or holds, a stop of P1. Nothing else about the click is read here (the click check above stays as it was), and a scroll alone is never an effect (M2 is unchanged). A scroll done with a transform instead of by scrolling is not seen: the candidate goes to J1 as before.

**Execute check** (HtT 2, "execute"; each custom control, at most `EXECUTE_MAX`). Fresh replay to the stop; press Enter and record the effect; if none, press Space and record it; if neither has an effect, a fresh replay to the stop followed by a mouse click on it, and its effect. Native controls are not executed: the browser activates them from the keyboard, and custom controls are where keyboard operation breaks (F42); this keeps a typical page inside the time budget (Abby, 2026-10-31). One exception (1.10.0, review E-08, Abby 2026-11-13; WCAG failure F54): a *pointer-only native control*, a native control that is not a link with an address (`a[href]`, `area[href]`: Enter follows the address) and has a `mousedown`, `mouseup`, `pointerdown` or `pointerup` listener of its own and no `click` listener of its own. The browser activates a native control from the keyboard by sending it a `click`, so one that answers only the pointer's down and up does nothing on Enter or Space. It is executed like a custom control, after them within `EXECUTE_MAX`, with the same rows (M8 to M10g). A `click` listener on an ancestor (delegation) works from the keyboard too, so Enter has the effect and the control passes M8. A control whose mouse-down effect is a ripple and whose click does nothing else reads as "the click has an effect, the keys do not" and FAILs: the accepted false FAIL (Abby: "rather risk a false fail than a false pass"). A second exception (1.16.0, issue #136 step 28; round 3, MySearchStory, key Fail: "Could reach the "Submit Your Story" and "SEARCH" buttons, but could not activate them with enter or space like I could with the mouse (they only advanced the carousel below the search bar)"): a native control that is a button (`button`; `input` of type button, submit, reset or image; `summary`) or a link with an address (`a[href]`, `area[href]`: a container that cancels Enter stops the link being followed) and has a *key-listening container*. Such a container can take Enter and Space for itself and cancel the click the browser would send the button (that page's carousel, ngx-bootstrap: Enter and Space advance the slide and call `preventDefault`). It is executed after the pointer-only native controls, within `EXECUTE_MAX`, with the same rows. Measured on the three rounds' 29 frozen pages (2026-11-21, top document, visible controls): 6 pages have any, at most 11 on one page (round 2's home page, 9 buttons and 2 links in its carousel); round 3's MySearchStory has 3 buttons (its carousel and the search bar's dropdown), SDE home 2, the search page 1; round 1's Careers and Artemis III pages 6 and 5 tab buttons, and the NACA feature 5 chapter links; the other 23 pages none. Custom controls are 0 or 1 a page on every report in git, except round 3's two Data Governance pages (61 and 76, over any limit), so one limit covers all three groups.

**What is recorded for each executed control** (1.16.0). A fresh replay to the stop and a mouse click on it, and its effect; a fresh replay to the stop and Enter, and its effect; when Enter's effect is not the click's, a fresh replay and Space, and its effect. The click is always recorded, because M8 now asks whether a key did what the click does, not only whether it did something (round 3, MySearchStory: Enter on the carousel itself advanced it, which passed M8, while a click on it did nothing). (Until 1.21.0, 4.F's pass R's Enter press on the stop was reused; 4.F 1.16.0 reads the shared walk instead, so 4.A presses Enter itself.)

**Opened content** (1.21.0; #135 step 15, fix 9b phase 2; Abby approved 2026-11-23, option a). TT asks the tester to access and execute every element (p. 19 HtT 2), drop-down menus and revealing content among them (p. 19 Identify Content). Each trigger `reveal.py` opened (guard RV's list) is read on a fresh load opened as it opened it (`reveal.reopen`: Enter, or a click when Enter showed nothing):
- *Reached.* An element there is reached when 4.C's P8 walk through that trigger's opened content ([4c-no-keyboard-trap.md](4c-no-keyboard-trap.md), section 2; `opened.py`) stopped on it or on something inside it or around it, or when the *onward Tabs* did. The onward Tabs (a fact of the shared walk, `opened.py`): when P8 left the opened content before reaching all of it, a load opened the same way is Tabbed from the opening with P1's rules until every opened element is reached, focus is back on the trigger, P1's stop count + 3 presses (at most 200), or the deadline; they are kept apart from P8's steps, so 4.C, 4.D, 4.E and 5.D read P8 unchanged. Round 3's SDE "All" menu stays open when focus leaves it, and Tab reaches its options after the search box, two buttons and a link.
- *Pointer scan.* The pointer targets that the opened state shows and the page's own scan did not list; those not reached are candidates, unless the arrow probe (above, from the P8 stop of the same widget or radio group, else from where the opening left focus, on a load opened the same way) or the radio probe (from that stop) reaches them. No second probe: 4.A's own, started from the opened state.
- *Hover scan.* Each stop reached inside the opened content is hovered, at most `HOVER_OPENED_MAX` a page; what that shows is reached when Enter on that stop, on a load opened the same way, shows it too (within `REVEAL_REPLAYS`), else a candidate.
- *Candidates* get the click check and the scroll check on a load opened the same way, and rows M3–M7 as any candidate.
- *Execute check.* A trigger `reveal.py` opened only by a click (Enter showed nothing) is executed first, ahead of `EXECUTE_MAX`'s other entries (Abby, 2026-11-15); rows M8–M10 decide (Enter has shown nothing, so it fails unless Space does the click's). Custom and pointer-only controls reached inside opened content are executed after the page's own, within `EXECUTE_MAX`, on a load opened the same way followed by the Tabs that reached them.
- *Title check.* Stops reached inside opened content with a title; *available elsewhere* also reads the opened state's text.
- *Steps to reproduce* open the trigger first ('press Enter on "All", then press Tab 9 times, then press Enter'); a control the onward Tabs reached is said to be reached "only after focus has left that menu".
Fixtures F44 (a menu Tab reaches once opened: PASS), F45 (a list that closes when focus leaves its button: its options are candidates, J1), F46 (round 3's "All" pattern: options reached only by the onward Tabs, Enter and Space do nothing, a click chooses: M10 FAIL; key Fail, issue 10), F47 (a menu that opens on a click only: M10 FAIL).

**Title check** (HtT 1.b, 2.a). Every stop with a non-empty title. Chrome does not show a title tooltip on keyboard focus (V2), so title text is never treated as revealed by focus. The title is *available elsewhere* (HtT 2.c) when, after collapsing whitespace and case, it equals the stop's accessible name or is contained in the page's visible text.

**Undetectable signals.** Things the scans cannot judge: a visible `<canvas>` at least 50 × 50 px; an element with `draggable=true` or its own drag, mousemove, pointermove, touch or wheel listener; `<object>` or `<embed>`; a frame the tool cannot read. Each counts only when it has a visible area: shown, and at least 1 CSS px each way (1.17.0, issue #136 step 32; Abby approved 2026-11-21): a frame or element a mouse cannot touch has nothing for a mouse to use. A listener on `window`, `document`, `html` or `body` is never a signal: it is the page's own scrolling, analytics or gesture handling, not a control. Round 3: every Drupal page was NEEDS REVIEW for AddToAny's utility frame (`display: none`, 0 × 0, `aria-hidden`, from another site, not in the recording) and its `#addtoany` strip (1280 × 0 px, its own `click` and `touchstart` listeners). The risk taken: a mouse-only feature built only on a `document`-level listener is not flagged. Fixtures F36 (both hidden: no signal) and F37 (both shown: two signals). Each is NEEDS REVIEW (M16), never a reason to PASS: a page with none of them and no other instance can PASS mechanically (G4), with the list of what was looked for (Abby, 2026-10-31).

**Time budget:** the pointer and hover scans are one load plus about 0.1 s per hovered stop; each click, execute or arrow probe is one fresh replay (about 2–5 s on a fixture page). Typical government pages with native controls only cost under 10 s. Replays to a stop use the 4.C replay rule (4.C spec section 2, 1.7.0; 1.1.2): measured on a realistic agency home page, 4.A's 13 replays take 32 s, down from 51 s; reusing pass W's arrows and pass R's Enter presses brought it to 20 s (pass R's no longer, since 4.F 1.16.0), and treating date-input parts as native takes the benefits form from 34 s to 5 s (1.2.0). 1.16.0: an executed control costs two or three replays (the click, Enter, and Space when Enter does not do the click's), where it cost one to three; most pages have no native control in a key-listening container (above). The whole run stays within `run_limit_s`; work not done in time is G3.

## 3. Mechanical checks

Instances: *K*, each unreached candidate; *X*, each custom control executed; *T*, each stop with title text; *U*, each undetectable signal.

## 4. Judgment questions

The calling agent answers each once, by the rubric; a person's answer overrides it. Page text and element names are evidence in `input`, never part of the question wording.

### J1. Is there another keyboard way to do the same thing?

**Question:** "input.candidate is something a mouse can use (with what clicking it did, and, as input.candidate.goes_to, the address it goes to when it goes anywhere; 1.8.1, fix 25) that keyboard focus never reaches. shared_inputs.stops lists, numbered, every element keyboard focus does reach, with role and name. Image A shows the page. Is there an element in shared_inputs.stops that does the same thing, so a keyboard user loses nothing? Answer alternative (with element: its number), no_alternative or unsure, with your reasons in a few plain words."

**Rubric.** alternative: a reached element plainly does the same job (a second print button, a text link with the same purpose, a field where Enter submits the same search). A reached link to the candidate's address is already matched by the tool (M3); a reached link to a different address is an alternative only if it plainly does the same job for another reason (1.8.1: the judge sees both addresses; the rubric does not lean either way). Only elements on this page count: a link to another page that might offer the same thing is not an alternative (p. 19 HtT 2.b, "available on the page"). no_alternative: nothing reached does that job. unsure: whenever the evidence does not settle it. Answer alternative only when you are sure it does the same job: if your reasons say it is not the same, is unclear or is not certain, the answer is unsure (1.16.0). The named number must be a stop, and reasons that are *hedged* make an alternative unsure (mechanical guards, M7).

### J2. Is this title information essential?

**Question:** "input.title is text that appears only as a mouse tooltip on the element in input.element; it is not shown on the page. input.element.name is the element's accessible name, which assistive technology announces. Is the title needed to use the element or understand the page (essential), or is it extra (not essential)? Answer essential, not_essential or unsure, with reasons."

**Rubric.** essential: instructions or a format needed to fill a field, the only label of an icon-only control when its name does not already say it, the meaning of an abbreviation needed to understand content, or anything else the title adds that a user needs and the name and page do not give. not_essential: a repeat or rewording of what the page or the element's name already says (the same meaning in other words, adding nothing a user needs); a link or control named by a feed or file format (RSS, Atom, PDF) whose title spells out that format for what is on the page ("(RSS)" with "View the current search as an RSS feed"); decoration. unsure: whenever the evidence does not settle it.

**Why the name counts (1.18.0, issue #136; Abby, 2026-11-21).** The title check already treats a title equal to the accessible name as available elsewhere (M11); a title that says the same thing in other words is the same case, and only a reading can tell that, so J2 decides it. Round 2's sort button (title "Toggle sort direction", name "Toggle order; currently descending order") was a FAIL against a Pass key because the rubric's icon-only example read as covering it. A title that adds to the name ("Sort" named, "Sort by release date, newest first" in the title) stays essential. Fixtures F38 (rewords: PASS, M13) and F39 (adds: FAIL, M14).

**A name that is a format (1.19.0, issue #136; Abby, 2026-11-22).** Round 2's search page, after 1.18.0: the "(RSS)" and "(Atom)" links, titles "View the current search as an RSS feed" and "View the current search as an Atom feed", were judged essential ("a bare abbreviation"), a FAIL against a Pass key; the run before had judged them not essential. Abby: they count as equivalent. A feed or file format named on the link is what the link is; a title that spells it out for this page adds nothing a user needs. Fixture F42 (PASS, M13).

## 6. What a FAIL records

Each FAIL instance records, to meet p. 5: the matching row (in the evidence trace only); location (frame chain, CSS path, role, name, link address); for K, what clicking it did, the stop whose hover reveals it, and J1's answer and reasons; for X, the effects of Enter, Space and the click, and the keys to reach it from a fresh load; for T, the title text and J2's answer; the page screenshot; and the tool versions the plan requires. Every instance is checked (up to the caps); a FAIL does not stop the scans.
